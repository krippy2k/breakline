# Breakline v0.3 — Impact Analysis

## Objective

Breakline v0.3 extends semantic change detection into **impact analysis**.

The goal of this release is to answer:

> **What could this behavioral change affect?**

Breakline should no longer stop at identifying that a function, method, class, or other symbol changed. It should construct a lightweight dependency graph around changed symbols and use that graph to identify their likely blast radius.

This release should remain focused on static analysis that is practical, explainable, and useful during code review. It does **not** need to become a complete compiler-grade call graph or whole-program analysis engine.

---

# Product Direction

Breakline's progression should look roughly like:

```text
git diff
    ↓
What lines changed?

semantic diff
    ↓
What code changed?

Breakline
    ↓
What behavior changed?
    ↓
What could that behavior affect?
```

v0.3 owns the final step.

The main reviewer experience should evolve from:

```text
OrderService.cancelOrder() changed.
```

into:

```text
HIGH IMPACT

OrderService.cancelOrder()

Behavioral change:
  Cancellation now permits PROCESSING orders.

Direct dependents:
  RefundProcessor.handleCancellation()
  AdminOrderService.cancel()
  OrderController.cancel()

Indirect dependents:
  POST /admin/orders/:id/cancel
  DELETE /orders/:id

Related tests:
  ✓ OrderService.cancelOrder()
  ✓ DELETE /orders/:id
  ⚠ RefundProcessor path has no detected test

Confidence: 0.88
```

---

# Primary Goals

v0.3 should provide:

1. A project-wide symbol index.
2. A lightweight dependency graph between symbols.
3. Impact traversal starting from changed symbols.
4. Direct and indirect dependent discovery.
5. Entry-point detection.
6. Related-test discovery.
7. Confidence scoring for inferred impact.
8. Human-readable CLI output.
9. Structured JSON output for future integrations.

---

# Non-Goals

Do **not** attempt to solve all of the following in v0.3:

- Full compiler-accurate call graph construction.
- Dynamic dispatch resolution across every language feature.
- Runtime tracing.
- True code coverage analysis.
- Taint analysis.
- Data-flow analysis across arbitrary object graphs.
- Inter-service distributed tracing.
- Cross-repository dependency analysis.
- GitHub UI integration.
- Risk scoring beyond simple impact heuristics.
- Automatic reviewer assignment.
- LLM-based reasoning as a hard dependency.

Those can come later.

---

# Supported Scope

Use the language support already established in Breakline v0.1/v0.2.

If multiple languages are supported, implement the impact architecture in a language-neutral way and add language-specific extractors behind interfaces.

If current support is TypeScript/JavaScript-first, prioritize correctness there.

# Core Concepts

## Symbol

A `Symbol` is a code entity Breakline can reason about.

Examples:

- function
- method
- class
- interface
- type
- variable
- exported constant
- route handler
- event handler
- CLI command
- test case

Suggested model:

```ts
export type SymbolKind =
  | "function"
  | "method"
  | "class"
  | "interface"
  | "type"
  | "variable"
  | "route"
  | "event-handler"
  | "cli-command"
  | "test"
  | "unknown";

export interface SymbolId {
  file: string;
  qualifiedName: string;
}

export interface CodeSymbol {
  id: SymbolId;
  name: string;
  qualifiedName: string;
  kind: SymbolKind;

  file: string;

  startLine: number;
  endLine: number;

  exported: boolean;
  isEntryPoint?: boolean;
  isTest?: boolean;

  metadata?: Record<string, unknown>;
}
```

The exact representation may differ, but symbol identity must be stable enough to connect references across files.

# Dependency Graph

Create a lightweight directed graph representing relationships between symbols.

## Edge Types

Start with:

```ts
export type DependencyKind =
  | "calls"
  | "imports"
  | "extends"
  | "implements"
  | "reads"
  | "writes"
  | "registers"
  | "references";
```

Not every edge type needs full support immediately.

Priority order:

1. `calls`
2. `imports`
3. `references`
4. `extends`
5. `implements`

Optional if straightforward:

6. `reads`
7. `writes`
8. `registers`

Suggested model:

```ts
export interface DependencyEdge {
  from: SymbolId;
  to: SymbolId;
  kind: DependencyKind;

  confidence: number;

  sourceLocation?: {
    file: string;
    line: number;
    column?: number;
  };
}
```

---

# Direction Semantics

Be explicit about edge direction.

For:

```ts
checkoutService.createOrder()
```

inside:

```ts
OrderController.checkout()
```

the graph should contain:

```text
OrderController.checkout()
    --calls-->
CheckoutService.createOrder()
```

When calculating impact for a changed symbol, Breakline should walk **reverse dependencies**.

Example:

```text
changed:
CheckoutService.createOrder()

reverse traversal finds:
OrderController.checkout()
```

The graph implementation should efficiently support:

```ts
graph.getDependencies(symbol)
graph.getDependents(symbol)
```

# Impact Model

Create a first-class impact result.

Suggested model:

```ts
export interface ImpactReference {
  symbol: CodeSymbol;

  distance: number;

  path?: SymbolId[];

  relation?: DependencyKind;

  confidence: number;
}

export interface EntryPointImpact extends ImpactReference {
  entryPointKind:
    | "http-route"
    | "event-handler"
    | "cli-command"
    | "export"
    | "public-api"
    | "unknown";
}

export interface TestImpact extends ImpactReference {
  testName?: string;
}

export interface ChangeImpact {
  changedSymbol: CodeSymbol;

  directDependents: ImpactReference[];
  indirectDependents: ImpactReference[];

  entryPoints: EntryPointImpact[];
  relatedTests: TestImpact[];

  maxDepthReached: number;

  confidence: number;
}
```

# Impact Traversal

Implement reverse graph traversal starting from each changed symbol.

Default:

```text
maxDepth = 3
```

This should be configurable.

Example graph:

```text
POST /checkout
      ↓
OrderController.checkout()
      ↓
CheckoutService.createOrder()
      ↓
calculatePrice()
```

If `calculatePrice()` changes:

```text
depth 1:
CheckoutService.createOrder()

depth 2:
OrderController.checkout()

depth 3:
POST /checkout
```

Expected classification:

```text
directDependents:
  CheckoutService.createOrder()

indirectDependents:
  OrderController.checkout()
  POST /checkout

entryPoints:
  POST /checkout
```

# Traversal Requirements

Traversal must:

- avoid infinite loops
- track visited symbols
- preserve shortest known path
- record traversal distance
- apply a max depth
- support filtering by edge type
- support confidence propagation

Pseudo-code:

```ts
function findImpact(
  changed: SymbolId,
  graph: DependencyGraph,
  maxDepth = 3
): ImpactReference[] {
  const queue = [{ symbol: changed, depth: 0, path: [changed] }];
  const visited = new Map<string, number>();

  const results: ImpactReference[] = [];

  while (queue.length > 0) {
    const current = queue.shift()!;

    if (current.depth >= maxDepth) {
      continue;
    }

    for (const edge of graph.getIncoming(current.symbol)) {
      const dependent = edge.from;
      const nextDepth = current.depth + 1;

      const key = serializeSymbolId(dependent);

      if (
        visited.has(key) &&
        visited.get(key)! <= nextDepth
      ) {
        continue;
      }

      visited.set(key, nextDepth);

      const path = [dependent, ...current.path];

      results.push({
        symbol: graph.symbols.get(dependent)!,
        distance: nextDepth,
        path,
        relation: edge.kind,
        confidence: edge.confidence
      });

      queue.push({
        symbol: dependent,
        depth: nextDepth,
        path
      });
    }
  }

  return results;
}
```

# Confidence

Impact analysis will sometimes be approximate.

Breakline should say so explicitly.

Do not pretend uncertain relationships are certain.

Suggested confidence interpretation:

```text
0.90–1.00  strong
0.70–0.89  likely
0.50–0.69  possible
< 0.50     weak
```

Initial rules can be simple.

Examples:

```text
direct resolved function call          0.98
resolved import reference              0.95
class inheritance                      0.95
same-file unresolved symbol reference  0.80
name-only project reference            0.60
heuristic route linkage                0.70
```

Path confidence may be computed as:

```ts
Math.min(...edgeConfidences)
```

or:

```ts
edgeConfidences.reduce((x, y) => x * y, 1)
```

Prefer the simpler and easier-to-explain approach initially.

# Entry Point Detection

Entry points are especially valuable because they connect implementation changes to user-visible or system-visible behavior.

Create an entry-point detector abstraction.

```ts
export interface EntryPointDetector {
  detect(
    symbol: CodeSymbol,
    context: AnalysisContext
  ): EntryPointInfo | undefined;
}
```

Initial entry-point categories:

## HTTP Routes

Detect common patterns when practical.

Examples:

```ts
app.get("/orders/:id", handler)
router.post("/checkout", checkout)
```

Framework support can grow incrementally.

Possible initial targets:

- Express
- Fastify
- NestJS decorators
- Next.js route handlers

Do not overbuild framework-specific logic if current Breakline language support is narrower.

---

## Event Handlers

Examples:

```ts
eventBus.on("order.cancelled", handler)
```

or:

```ts
consumer.subscribe(...)
```

Initial detection can be heuristic.

---

## CLI Commands

Examples:

```ts
program.command("migrate")
```

or known CLI entry files.

---

## Public Exports

If no framework entry point is detectable, top-level exported symbols can serve as lower-confidence public entry points.

# Test Discovery

v0.3 should identify tests likely related to changed or impacted symbols.

This is **not code coverage**.

Use static relationships.

Possible signals:

1. A test file imports the changed symbol.
2. A test calls the changed symbol.
3. A test calls an impacted dependent.
4. A test file name corresponds to a source module.
5. A test references an exported class/method.
6. A test name contains the changed symbol name.

Suggested confidence:

```text
direct test call/import               high
test imports dependent                medium-high
filename/module correspondence        medium
name heuristic only                   low
```

If current parser exposes calls such as:

# Missing-Test Signal

Breakline may emit:

```text
Potential test gap
```

when:

- a changed symbol has meaningful impact
- an important dependent or entry point is identified
- no related test can be found

Do not phrase this as certainty.

Use wording such as:

```text
No related test detected.
```

not:

```text
This code is untested.
```

# Impact Level

Do not build sophisticated risk scoring yet.

A simple impact classification is enough.

Example:

```ts
export type ImpactLevel =
  | "low"
  | "medium"
  | "high";
```

Possible initial heuristic:

### LOW

```text
0–1 direct dependents
no detected entry points
```

### MEDIUM

```text
2–5 dependents
or one detected entry point
```

### HIGH

```text
>5 dependents
or multiple entry points
or high-fan-out shared symbol
```

This should remain explicitly heuristic.

# Parsing and Resolution Strategy

Prefer existing parser infrastructure.

Do not introduce a heavyweight compiler dependency unless necessary.

For TypeScript, possible levels of resolution:

## Level 1

Same-file call resolution.

```ts
function a() {
  b();
}
```

Resolve `a -> b`.

## Level 2

Imported symbol resolution.

```ts
import { calculatePrice } from "./pricing";

calculatePrice(order);
```

Resolve the import path and connect caller to imported symbol.

## Level 3

Class method resolution.

```ts
service.cancelOrder();
```

Resolve when the type or imported class is statically obvious.

Do not require perfect resolution of all polymorphic calls.

# Performance

Impact analysis should be fast enough for local code review workflows.

Target for medium repositories:

```text
< 5 seconds
```

where practical.

Do not prematurely optimize, but avoid obvious O(N²) symbol scans.

Prefer:

```ts
Map<string, CodeSymbol[]>
Map<SymbolId, DependencyEdge[]>
```

for lookup and traversal.

# Caching

Caching is optional in v0.3.

However, design graph/index structures so future caching is possible.

Potential future artifact:

```text

```

Do not make cache correctness part of this release unless it is already easy to support.

# Explainability Requirement

Every reported impact should be explainable.

If Breakline says:

```text
POST /checkout is impacted
```

the user should be able to ask for or display the path:

```text
POST /checkout
  → checkout()
  → createOrder()
  → calculatePrice()
```

Never produce opaque impact claims with no traceable relationship.

---

# Failure Behavior

Impact analysis should degrade gracefully.

If resolution fails:

```text
Behavioral change detected.

Impact analysis:
  Unable to confidently resolve project dependents.
```

The overall Breakline analysis should still succeed.

Do not fail the entire CLI because one symbol cannot be resolved.

# Cursor Implementation Instructions

When implementing v0.3:

1. Inspect the existing Breakline architecture before creating new modules.
2. Reuse existing AST, parser, repository, diff, and semantic-analysis abstractions.
3. Do not rewrite working v0.1/v0.2 functionality.
4. Keep impact analysis independent from CLI formatting.
5. Prefer small, testable abstractions.
6. Add tests alongside each new graph or analysis component.
7. Avoid language-specific logic in core graph structures.
