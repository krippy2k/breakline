# Breakline v0.4 Specification
## GitHub App + Pull Request Reports

**Version:** 0.4  
**Status:** Proposed  
**Primary Goal:** Make Breakline usable directly in GitHub pull request workflows through an installable GitHub App that automatically analyzes pull requests and publishes Breakline reports back to GitHub.

---

## 1. Overview

Breakline v0.4 introduces the first full GitHub-native workflow.

A repository owner installs the Breakline GitHub App, enables it for one or more repositories, and Breakline automatically analyzes supported pull requests. Results are surfaced directly on the pull request using GitHub Checks, with links to a richer Breakline report when additional detail is available.

The GitHub App should feel like a thin integration layer around the existing Breakline analysis engine rather than a second implementation of Breakline.

The desired workflow is:

```text
Developer opens or updates PR
        ↓
GitHub sends webhook to Breakline
        ↓
Breakline resolves base + head revisions
        ↓
Breakline analyzes behavioral impact
        ↓
Breakline produces structured report
        ↓
GitHub Check Run is created/updated
        ↓
Reviewer sees summary, risk, and findings in PR
```

v0.4 should establish the architectural foundation for later GitHub-native functionality such as inline annotations, policy enforcement, reviewer assistance, historical reports, organization dashboards, and additional source-control providers.

---

# 2. Goals

## 2.1 Primary Goals

v0.4 must:

1. Provide an installable GitHub App for Breakline.
2. Receive pull request webhook events from GitHub.
3. Authenticate as the GitHub App installation.
4. Retrieve enough repository and pull request information to run Breakline analysis.
5. Run Breakline against the pull request's base and head revisions.
6. Create a GitHub Check Run representing the Breakline analysis.
7. Update that Check Run as analysis progresses and completes.
8. Show a concise Breakline summary directly in GitHub.
9. Link from GitHub to a detailed Breakline report when a hosted report is available.
10. Re-run analysis when the pull request changes.
11. Avoid duplicate reports or comments when a PR is updated.
12. Preserve a clean separation between:
    - Breakline Core
    - GitHub integration
    - report rendering
    - persistence / hosted services

---

# 3. Non-Goals

The following are explicitly out of scope for v0.4 unless required to support the primary workflow:

- GitHub Marketplace billing
- GitLab or Bitbucket integrations
- Organization-wide analytics dashboards
- historical trend analysis
- automatic code modification
- automatic pull request approval
- full AI code review
- merge blocking based on policy
- reviewer assignment
- repository indexing unrelated to the current PR
- long-term source-code storage
- advanced account management
- enterprise SSO
- multi-tenant billing
- complex permissions administration
- IDE integration

These may be built later on top of the v0.4 architecture.

# 4. User Experience

## 4.1 Installation

A user installs the Breakline GitHub App from an installation URL.

The user chooses either:

- all repositories, or
- selected repositories.

After installation, GitHub redirects the user to Breakline.

For v0.4, the post-installation page can be minimal.

Example:

```text
Breakline is connected.

Organization: Acme
Repositories:
✓ api
✓ web
✓ payments

Breakline will analyze new and updated pull requests.
```

---

## 4.2 Pull Request Workflow

When a pull request is opened, reopened, or updated:

1. GitHub sends a webhook.
2. Breakline validates the webhook signature.
3. Breakline records or queues an analysis request.
4. Breakline creates a Check Run:

```text
Breakline
Analyzing behavioral impact...
```

5. Breakline runs the analysis.
6. The Check Run is updated with the result.

Example completed output:

```text
Breakline

Behavioral Impact: HIGH

5 behavioral changes detected
2 high-confidence findings
1 possible authorization impact

Key findings

• Authorization predicate widened in authorizePayment()
• Retry behavior changed from 3 attempts to unlimited
• Validation no longer rejects missing customerId

View full Breakline report →
```

# 5. GitHub Surface

## 5.1 Primary Surface: Check Runs

Breakline should use the GitHub Checks API as the primary PR integration.

Check name:

```text
Breakline
```

Recommended states:

```text
queued
in_progress
completed
```

Recommended conclusions:

```text
success
neutral
failure
action_required
```

For v0.4:

- `success` means analysis completed and no significant behavioral findings were discovered.
- `neutral` means analysis completed and findings exist but Breakline is informational.
- `failure` should be reserved for analysis/runtime failure, not simply because findings exist.
- `action_required` may be used later for policy enforcement.

Breakline v0.4 should default to **informational**, not merge-blocking.

---

## 5.2 Check Run Summary

The GitHub Check summary should contain:

- overall impact level
- total findings
- finding counts by severity or confidence
- short description of the most important findings
- link to full Breakline report
- analysis metadata

Example:

```markdown
## Breakline Report

**Behavioral Impact:** High  
**Findings:** 5  
**High Confidence:** 2

### Key Findings

1. Authorization condition widened in `authorizePayment()`
2. Retry limit removed in `processTransaction()`
3. Missing `customerId` is no longer rejected

[View full report in Breakline]
```

The summary must remain intentionally compact.

GitHub is the entry point.

The detailed report belongs in Breakline.

v0.4 may support a repository setting:

```yaml

```

When enabled, Breakline creates one persistent pull request comment.

The comment must be updated rather than recreated on every push.

Example:

```markdown

**Impact: High**

Breakline detected 5 behavioral changes.

- 2 high-confidence findings
- 1 authorization-related change
- 1 validation change
- 1 error-flow change

```

Breakline should embed an invisible marker so it can locate its own comment:

```html
<!-- breakline-report -->
```

The Check Run remains the canonical GitHub integration.

# 8. Webhook Endpoint

Initial endpoint:

```text
POST /api/github/webhooks
```

Responsibilities:

1. Read raw request body.
2. Validate `X-Hub-Signature-256`.
3. Read:
   - `X-GitHub-Event`
   - `X-GitHub-Delivery`
4. Reject invalid signatures.
5. Detect duplicate deliveries.
6. Dispatch supported events.
7. Return quickly.

Webhook processing should not synchronously perform the full Breakline analysis.

Recommended:

```text
Webhook
   ↓
Validate
   ↓
Normalize event
   ↓
Enqueue analysis job
   ↓
HTTP 202
```

---

# 9. Idempotency

GitHub can retry webhook deliveries.

Breakline must record the GitHub delivery ID:

```text
X-GitHub-Delivery
```

A delivery should only be processed once.

At minimum:

```text
github_delivery_id
received_at
event_type
status
```

Duplicate delivery IDs should return success without re-running analysis.

---

# 10. GitHub Authentication

Breakline should authenticate using standard GitHub App authentication.

## 10.1 App JWT

Breakline signs a short-lived JWT using the GitHub App private key.

The JWT is used to request an installation access token.

## 10.2 Installation Token

Breakline requests an installation token:

```text
POST /app/installations/{installation_id}/access_tokens
```

The installation token is then used for repository access.

Installation tokens must:

- remain in memory or encrypted transient storage
- never be logged
- never be exposed in reports
- be refreshed as necessary

---

# 11. GitHub App Permissions

Start with the minimum required permissions.

Recommended repository permissions:

```text
Checks: Read & Write
Contents: Read
Metadata: Read
Pull Requests: Read
```

Optional if PR comments are enabled:

```text
Issues: Read & Write
```

GitHub pull request comments use the Issues API, so comment support may require Issues write permission.

Avoid requesting:

- administration
- workflows
- secrets
- deployments
- members
- organization administration

unless a future feature explicitly requires them.

# 12. Repository Retrieval Strategy

Breakline needs the base and head source trees.

Two implementation strategies are acceptable.

## Option A — Git Clone

Perform a shallow authenticated clone/fetch.

Example conceptual workflow:

```text
git init
git remote add origin <repo>
git fetch origin <base_sha> --depth=1
git fetch origin <head_sha> --depth=1
```

Advantages:

- closest to CLI behavior
- easy reuse of existing Git analysis
- supports arbitrary repository inspection
- simpler local reproduction

Disadvantages:

- repository download cost
- credential handling
- storage cleanup

## Option B — GitHub Contents / Git Data APIs

Fetch files using GitHub APIs.

Advantages:

- no clone
- potentially smaller transfer

Disadvantages:

- more integration complexity
- awkward for broad repository analysis
- rate-limit pressure
- diverges from local Breakline behavior

### v0.4 Recommendation

Use **shallow Git fetch/clone**.

The hosted analysis path should invoke the same Breakline engine used locally.

Each analysis should be uniquely identified by:


Repeated webhook events with the same:

```text

```

# 15. Breakline Core Integration

The GitHub integration must not contain behavioral-analysis logic.

Preferred boundary:

```ts
interface AnalysisRequest {
  repositoryPath: string;
  baseRevision: string;
  headRevision: string;
  config?: BreaklineConfig;
}

interface BreaklineReport {
  version: string;
  summary: AnalysisSummary;
  findings: Finding[];
  metadata: AnalysisMetadata;
}

async function analyze(
  request: AnalysisRequest
): Promise<BreaklineReport>;
```

GitHub-specific code is responsible for translating:

```text
GitHub PR → AnalysisRequest
```

and:

```text
BreaklineReport → GitHub Check Run
```

# 17. Structured Report Contract

The GitHub integration should consume the structured Breakline report rather than CLI text.

Minimum report shape:

```ts
interface BreaklineReport {
  schemaVersion: string;

  analysis: {
    id: string;
    baseRevision: string;
    headRevision: string;
    startedAt: string;
    completedAt: string;
  };

  summary: {
    impact: "none" | "low" | "medium" | "high";
    findingCount: number;
    highConfidenceCount: number;
  };

  findings: Finding[];
}
```

Example finding:

```ts
interface Finding {
  id: string;

  category:
    | "control-flow"
    | "validation"
    | "authorization"
    | "error-flow"
    | "return-value"
    | "side-effect"
    | "boundary"
    | "call-behavior"
    | "other";

  severity: "info" | "low" | "medium" | "high";

  confidence: "low" | "medium" | "high";

  title: string;
  description: string;

  location?: {
    path: string;
    startLine?: number;
    endLine?: number;
  };

  evidence?: Evidence[];
}
```

The exact schema may already exist from earlier milestones; v0.4 should extend rather than duplicate it.

# 18. Risk / Impact Classification

v0.4 should expose one overall PR impact value:

```text
none
low
medium
high
```

The impact classification should be deterministic.

Example initial policy:

```text
HIGH
- any high-severity + high-confidence finding
- authorization behavior changed
- validation removed from a security-sensitive path

MEDIUM
- multiple medium findings
- meaningful error/control-flow behavior changed

LOW
- limited behavioral change
- low-confidence behavioral differences

NONE
- no supported behavioral changes detected
```

The classifier should live outside the GitHub rendering layer.

GitHub only displays the result.

# 23. Inline Annotations

Inline Check annotations are desirable but **not required for the initial v0.4 acceptance criteria**.

If easy to support, Breakline may publish annotations for findings with precise changed-line locations.

Example:

```text
src/auth/payment.ts:84
Breakline: Authorization predicate widened.
```

Constraints:

- annotate only high-confidence findings
- annotate only when source location maps correctly to the PR diff
- avoid excessive annotation volume
- cap annotations per run

A reasonable default cap:

```text
10 annotations
```

Additional findings remain available in the full report.

# 25. Draft Pull Requests

Default behavior:

```text
Draft PR → analyze
```

Reason:

Behavioral feedback can be useful before a PR is ready for review.

Repository config may later allow:

```yaml
github:
  analyzeDrafts: false
```

This does not need to be exposed in UI for v0.4.

---

# 26. Fork Pull Requests

Fork PRs need special handling because the head repository may differ from the base repository.

Breakline must use the commit SHAs supplied by GitHub rather than assuming:

```text
origin/<branch-name>
```

The implementation should be tested against:

- same-repository PR
- fork PR from public repository

Private fork behavior can be deferred if GitHub permission constraints prevent access.

---

# 27. Reanalysis

Breakline should re-run automatically on:

```text
pull_request.opened
pull_request.reopened
pull_request.synchronize
pull_request.ready_for_review
```

Only the newest head SHA should be considered current.

If an older queued analysis has not started when a newer commit arrives, it may be canceled.

If an old analysis is already running, v0.4 may either:

1. allow it to finish but suppress publication if stale, or
2. cancel it if the infrastructure supports cancellation.

Minimum requirement:

**Never overwrite a newer PR report with results from an older head SHA.**

Before publishing, confirm that the analysis head SHA still matches the relevant run.

# 31. Job Queue

Webhook handling and analysis should be decoupled.

Abstract interface:

```ts
interface AnalysisQueue {
  enqueue(job: PullRequestAnalysisJob): Promise<void>;
}
```

Initial implementations could use:

- database-backed queue
- Redis / BullMQ
- SQS
- local in-process queue for development

The domain logic should not depend on the queue implementation.

Job:

```ts
interface PullRequestAnalysisJob {
  installationId: number;
  repositoryId: number;
  owner: string;
  repo: string;
  pullRequestNumber: number;
  baseSha: string;
  headSha: string;
}
```

# 32. Security Requirements

## Required

- Validate every GitHub webhook signature.
- Do not trust repository values from arbitrary requests.
- Keep the GitHub App private key outside source control.
- Never log installation access tokens.
- Use least-privilege GitHub permissions.
- Delete temporary repository clones after analysis.
- Prevent path traversal when using repository-provided paths.
- Treat repository content as untrusted input.
- Do not execute repository code during static analysis.
- Do not run package install hooks.
- Do not run arbitrary repository scripts.
- Set limits on repository size and analysis time.
- Sanitize rendered Markdown where appropriate.
- Escape user-controlled values used in shell commands.

---

# 33. Repository Isolation

Each analysis must execute in an isolated temporary working directory.

Example:

```text
/tmp/breakline/<analysis-id>/
```

After analysis:

```text
rm -rf /tmp/breakline/<analysis-id>
```

Cleanup should run on success and failure.

Longer-term, analysis may run in containers or isolated workers.

Containerization is recommended but not mandatory for v0.4 if Breakline does not execute repository code.

---

# 34. Limits

Initial guardrails:

```text
Maximum changed files: configurable
Maximum repository checkout size: configurable
Maximum analysis duration: configurable
Maximum GitHub findings displayed: 5
Maximum inline annotations: 10
```

If limits are exceeded, Breakline should generate a partial or explanatory report instead of silently failing.

Example:

```text
Breakline analyzed 150 of 487 changed files.

Analysis was limited by the repository safety threshold.
```

# 43. Required v0.4 End-to-End Scenario

The release is not complete until this workflow succeeds against a real GitHub repository:

1. Install Breakline GitHub App.
2. Enable a repository.
3. Open a pull request containing a supported behavioral change.
4. GitHub sends the webhook.
5. Breakline creates an in-progress Check Run.
6. Breakline analyzes the correct base and head SHAs.
7. Breakline identifies the expected behavioral change.
8. Breakline updates the Check Run.
9. The PR shows the Breakline result.
10. The Check contains a link to the detailed report.
11. Push another commit.
12. GitHub sends `synchronize`.
13. Breakline analyzes the new head SHA.
14. The newest result becomes the visible/current report.
15. No duplicate persistent PR comment is created.

# 49. v0.4 Product Principle

The GitHub integration should not try to become another general-purpose code-review bot.

Breakline's distinctive value is:

```text
"What behavior changed?"
```

not merely:

```text
"What lines changed?"
```

Every GitHub surface in v0.4 should reinforce that distinction.

The ideal reviewer reaction is:

```text
"I can see what this pull request changes behaviorally before I start reading every line."
```
