# Breakline v0.2

**Cursor Implementation Plan**

Milestone: Behavioral Findings for TypeScript code changes

Purpose: This document is intended to be given directly to Cursor as
implementation context and a scoped build plan for Breakline v0.2.

## 1. v0.2 Goal

Breakline v0.2 should move beyond structural AST differences and begin
reporting behavior-affecting changes in modified TypeScript functions.

Given two revisions of a TypeScript codebase, Breakline should identify
a useful, intentionally limited set of behavioral changes, convert them
into stable findings, and expose those findings through both
human-readable CLI output and machine-readable JSON.

The goal is not formal semantic equivalence. v0.2 should favor
deterministic, explainable heuristics that developers can trust.

## 2. Product Principle

Breakline should answer:

``` text

“What changed about what this code does?”
```

rather than merely:

``` text

“What syntax changed?”
```

Every v0.2 feature should be evaluated against that distinction.

## 3. Scope

In scope for v0.2:

-   Changed TypeScript functions and methods.

-   Function signature changes.

-   Return-expression and return-path changes.

-   Conditional-expression changes.

-   Function/method calls added or removed.

-   Call argument changes.

-   Throw statements and basic exception-behavior changes.

-   Stable behavioral Finding objects.

-   Readable terminal output.

-   JSON output suitable for CI and future integrations.

-   Tests using small before/after source fixtures.

Explicitly out of scope:

-   Formal proof that two implementations are behaviorally equivalent.

-   Runtime execution or generated tests.

-   Whole-program data-flow analysis.

-   Cross-service or distributed-system behavior.

-   AI/LLM-generated explanations as a required part of analysis.

-   Full dependency-impact analysis.

-   Every possible JavaScript/TypeScript semantic edge case.

## 5. Core Domain Model

Introduce a clean separation between raw structural changes and
user-facing behavioral findings. Adapt names to the existing codebase
where appropriate, but preserve the conceptual boundary.

``` text

export type ChangeKind =
  | "function_added"
  | "function_removed"
  | "signature_changed"
  | "return_changed"
  | "condition_changed"
  | "call_added"
  | "call_removed"
  | "call_arguments_changed"
  | "throw_added"
  | "throw_removed";

export interface SourceLocation {
  file: string;
  line?: number;
  column?: number;
}

export interface Change {
  kind: ChangeKind;
  symbol?: string;
  before?: unknown;
  after?: unknown;
  location?: SourceLocation;
}

export type FindingSeverity = "info" | "warning";

export interface Finding {
  id: string;
  kind: ChangeKind;
  symbol: string;
  summary: string;
  detail?: string;
  before?: string;
  after?: string;
  location?: SourceLocation;
  severity: FindingSeverity;
}
```

Finding IDs should be deterministic where practical so later CI
integrations can compare or suppress findings.

## 6. Implementation Steps

### Step 1 - Establish the Change Classifier

Create a classifier layer whose input is the existing structural diff
representation and whose output is Change\[\]. Do not put presentation
logic into the classifier.

-   Define ChangeKind and Change.

-   Create a classifier entry point, e.g. classifyChanges(diff):
    Change\[\].

-   Ensure classifiers can be added independently.

-   Add unit tests before expanding classification rules.

Acceptance criteria:

-   A changed function can be passed through the classifier.

-   The classifier returns deterministic Change objects.

-   No CLI formatting is required inside classification code.

### Step 2 - Function Signature Changes

Detect behaviorally relevant changes to function and method interfaces.

-   Parameter added or removed.

-   Parameter order changed.

-   Optional/required status changed.

-   Default value changed.

-   Return type changed when explicitly declared.

-   Async modifier added or removed.

``` text

Example finding:

processOrder()
  SIGNATURE CHANGED

  Parameter "options" is now required.

```

### Step 3 - Conditional Changes

Compare conditions used by if statements, conditional expressions,
loops, and guards. Start with normalized expression comparison rather
than attempting theorem proving.

Useful first-pass cases:

-   Operator changed: \> to \>=, === to !==, && to \|\|, etc.

-   Literal or identifier changed inside a condition.

-   A conjunct/disjunct was added or removed.

-   A guard condition was added or removed.

``` text

Before:
if (order.status === "pending") { ... }

After:
if (order.status !== "shipped") { ... }

Finding:
Cancellation condition changed:
  before: order.status === "pending"
  after:  order.status !== "shipped"

```

Do not claim that a condition was 'widened' or 'narrowed' unless the
classifier can establish that safely. Otherwise use neutral language
such as 'condition changed'.

### Step 4 - Return Behavior

Detect meaningful changes to explicit return statements.

-   Return expression changed.

-   Return added or removed.

-   Literal return changed.

-   Returned identifier/call changed.

-   Basic change in the number of return paths.

Keep this structural and explainable. More sophisticated control-flow
reasoning can come later.

### Step 5 - Call-Site Changes

Within changed functions, compare call expressions.

-   Call added.

-   Call removed.

-   Callee changed.

-   Arguments changed.

-   Argument count changed.

``` text

Before:
save(order);

After:
save(order);
auditOrder(order.id);

Finding:
New call:
  auditOrder(order.id)

```

This is especially important because newly introduced calls often
represent new side effects even when Breakline cannot yet prove that a
call is side-effecting. Phrase findings as calls, not guaranteed side
effects.

### Step 6 - Basic Exception Behavior

Add conservative detection around explicit throw statements.

-   throw added.

-   throw removed.

-   Thrown expression changed.

``` text

Before:
return null;

After:
throw new OrderNotFoundError(id);

Finding:
Exception behavior changed:
  function now explicitly throws OrderNotFoundError.

```

Do not attempt to infer all exceptions reachable through called
functions in v0.2.

### Step 7 - Finding Generation

Convert Change objects into Finding objects in a separate layer.

Responsibilities:

-   Generate concise summaries.

-   Preserve before/after expressions where useful.

-   Attach symbol and source location.

-   Assign conservative severity.

-   Generate deterministic IDs.

-   Avoid speculative language.

The Finding layer should be reusable by the CLI, JSON formatter, future
GitHub integration, and future IDE tooling.

### Step 8 - CLI and JSON Output

Human-readable output should emphasize files, symbols, and findings
rather than AST internals.

``` text

BREAKLINE  src/orders.ts

processOrder()
  BEHAVIOR CHANGED

  • Condition changed
      before: status === "pending"
      after:  status !== "shipped"

  • New call
      auditOrder(order.id)

  • Return behavior unchanged

```

Suggested CLI options:

``` text

breakline <before> <after>
breakline <before> <after> --format text
breakline <before> <after> --format json
breakline <before> <after> --output findings.json
```

JSON should serialize a versioned result envelope so the format can
evolve.

``` text

{
  "schemaVersion": "0.2",
  "files": [
    {
      "path": "src/orders.ts",
      "findings": []
    }
  ]
}
```

## 7. Testing Strategy

Prefer small fixture pairs that isolate one behavior. Each classifier
should have positive and negative tests.

Minimum fixture matrix:

-   No behavioral change / formatting-only change.

-   Parameter added.

-   Default parameter changed.

-   Condition operator changed.

-   Condition operand changed.

-   Return expression changed.

-   Call added.

-   Call removed.

-   Call arguments changed.

-   Throw added.

-   Throw removed.

-   Multiple findings in one function.

-   Multiple changed functions in one file.

Snapshot tests are appropriate for CLI output, but classifier behavior
should primarily use explicit object assertions so formatting changes do
not hide analysis regressions.

## 9. Definition of Done

Breakline v0.2 is complete when:

-   Two TypeScript revisions can be analyzed through the normal
    Breakline CLI flow.

-   Modified functions produce behavioral findings for the scoped
    categories.

-   Formatting-only or irrelevant AST changes do not produce behavioral
    findings.

-   Findings include enough before/after context to be understandable
    without inspecting raw AST.

-   Text and JSON output are generated from the same Finding model.

-   The JSON schema is versioned.

-   All classifier categories have fixture-based tests.

-   The README contains at least one realistic before/after v0.2
    example.

-   No finding makes a semantic claim Breakline cannot justify from its
    analysis.

## 10. Cursor Execution Instructions

When implementing this plan:

-   Inspect the existing Breakline architecture first. Reuse current AST
    and diff abstractions rather than replacing them.

-   Implement one classifier at a time and keep commits/build steps
    small.

-   Run the existing test suite after every structural change.

-   Add tests before broadening a heuristic.

-   Prefer deterministic AST-based rules over clever but opaque
    inference.

-   Keep analysis, finding generation, and output formatting separate.

-   Do not add an LLM dependency for v0.2.

-   Do not silently expand scope into control-flow, interprocedural, or
    runtime analysis.

-   When the existing architecture conflicts with this document,
    preserve working architecture and map these concepts onto it
    cleanly.

## 11. Suggested Build Order

1.  Domain types and classifier interface.

2.  Signature classifier.

3.  Call classifier.

4.  Return classifier.

5.  Condition classifier.

6.  Exception classifier.

7.  Finding generation.

8.  Text formatter.

9.  JSON formatter/schema version.

10. End-to-end fixtures and README example.

## 12. v0.2 Non-Goals / Future Hooks

Do not implement these now, but avoid architecture that makes them
difficult later:

-   Control-flow graph comparison.

-   Interprocedural impact analysis.

-   State-machine inference.

-   Dependency-impact propagation.

-   Runtime trace comparison.

-   Generated tests / counterexamples.

-   GitHub PR annotations.

-   IDE diagnostics.

-   LLM-assisted explanation layered on deterministic findings.

-   Confidence scoring and finding suppression.

## 13. First Cursor Task

Start here before implementing all of v0.2:

``` text

TASK: Introduce the behavioral change-classification layer.

1. Inspect the existing AST/diff pipeline and identify the narrowest stable
   representation from which behavioral changes can be classified.

2. Add ChangeKind and Change domain types.

3. Add a classifyChanges(...) entry point without changing current CLI behavior.

4. Implement the first classifier: function signature changes.

5. Add focused before/after fixtures and unit tests.

6. Keep presentation/output completely separate.

7. Run the full existing test suite and report:
   - files changed
   - architectural decisions made
   - tests added
   - any existing design constraints discovered
   - recommended next classifier

Do not implement the remaining classifiers until this foundation is clean.

```

## 14. Expected v0.2 Outcome

At the end of v0.2, Breakline should be able to inspect an ordinary code
change and produce a compact explanation of the most obvious ways the
behavior of modified functions changed. It will not understand
everything the program can do, but it should already provide information
that is materially more useful than a syntax-aware diff.

That becomes the foundation for deeper semantic analysis in v0.3 and
beyond.
